# 実装レビュー

## スコープ

実装（貸出・返却）バックログの全成果物（`backend/app/schemas.py`・`backend/app/crud.py`・`backend/app/services.py`・`backend/app/main.py`の貸出・返却追加部分、`frontend/src/`配下の貸出・返却関連修正ファイル）を対象に、`運用ルール/開発ルール/レビュー工程ルール.md`に従い実装レビュー工程を実施する。`実装_チェックリスト.md`・`FastAPI/Pydantic/SQLAlchemy/React_実装_チェックリスト.md`の各項目で確認した。

## レビュー結果

- 各チェックリストの全項目を確認した結果、指摘事項は見つからなかった。
- レビュー工程ルール「指摘が無ければレビュー指摘表の作成は不要」に基づき、レビュー指摘表は作成していない。
- `schemas.py`の`LoanRequestReturnRequest`・`LoanLendReturnResponse`の項目名・型・最大桁（`return_note`：`str | None`・最大200文字）が、設計書（`設計書/スキーマ（schemas）/貸出・返却操作_v1.0.0.md`）と1対1で一致していることを確認した。
- `main.py`の`lend_loan_request_endpoint`・`return_loan_request_endpoint`が、既存の管理者専用エンドポイント（`admin_cancel_loan_request_endpoint`等）と同じ依存性注入パターン（`auth.require_admin`→`auth.require_password_changed`→`get_db`）で実装されており、認証層でブロック済みの条件（管理者ロール・初回パスワード変更）を業務ロジック側で二重に実装していないことを確認した。
- レイヤー構成（main.py→services.py→crud.pyの一方向呼び出し）を、本バックログの新規エンドポイント（貸出処理・返却処理）および日次バッチ本体（ノーショー自動取消・期限通知生成。`scheduler.py`から遅延importで呼び出され、エンドポイントを持たない）で確認し、違反がないことを確認した。
- 以下の3パターンについて、実際のAPI呼び出しでは到達不能な状態（業務ルール上、正規のAPI操作列では再現できない状態）であることを個別に確認した上で、disposable SQLiteへの直接のDB操作でその状態を再現し、`lend_loan_request`・`auto_cancel_stale_requests`内の防御的チェックが設計どおりに動作することを機能テスト（disposable SQLite + FastAPI `TestClient`）で確認した。
    - 「無効化された備品に対する貸出処理」：`disable_equipment`が有効な貸出申請を持つ備品の無効化自体を400で拒否するため、通常のAPI操作列では再現不能。備品の`is_active`列を直接書き換えて再現し、`lend_loan_request`が400を返すことを確認した。
    - 「開始日が過去の承認済み申請」：`approve_loan_request`が開始日過去の承認待ち申請の承認自体を400で拒否するため、通常のAPI操作列では再現不能。開始日・返却予定日当日の申請を承認した後、`due_date`列を直接過去日に書き換えて再現し、`auto_cancel_stale_requests`が「承認済みで返却予定日超過」の条件で検出・取消することを確認した。
    - 「開始日が過去の申請中申請（ノーショーパターン1）」：`create_loan_request`は開始日の過去日を作成時点でブロックしないため、通常のAPI呼び出しのみで再現可能であることを確認し、`auto_cancel_stale_requests`が「申請中で開始日超過」の条件で検出・取消することを確認した。
- 貸出処理（F10）について、承認済み申請の貸出成功、承認待ち申請への貸出の400拒否、開始日前の承認済み申請への貸出の400拒否、存在しない申請IDへの404、同一備品の二重貸出の400拒否を機能テストで確認した。
- 返却処理（F11）について、貸出中申請の返却成功（状態メモあり・なしの両方）、既に返却済みの申請への再返却の400拒否、申請中・承認済み申請への返却の400拒否、存在しない申請IDへの404を機能テストで確認した。
- 日次バッチ本体について、`crud.get_stale_loan_requests`・`crud.get_due_reminder_loan_requests`の抽出条件（承認済み×返却予定日超過、申請中×開始日超過、貸出中×返却予定日が明日、貸出中×返却予定日超過（期限超過中は毎日再通知））が設計書どおりであることを機能テストで確認し、`auto_cancel_stale_requests`が対象申請を取消済み状態に更新し取消通知（`cancelled`）を生成すること、`generate_due_reminder_notifications`が対象申請の申請者へ期限通知（`due_reminder`）を生成することを確認した。
- フロントエンド（`RequestManagementPage.tsx`への貸出処理・返却処理セクション追加）について、Playwright（`frontend/node_modules`に既存インストール済みのPlaywrightパッケージを直接`require`する方式。本バックログ用に新規作成したdisposableスクリプトで実施し、確認後に削除した）を用いて実際にブラウザ（Chromium）を起動し、開発サーバー（バックエンド：disposable SQLiteで`uvicorn`起動、フロントエンド：`npm run dev`のVite開発サーバー）に対して以下の一連の操作を実施し、画面が設計どおりに動作することを確認した。
    - 管理者ログイン→初回パスワード変更→一般ユーザー作成・備品登録（検証用、API経由）→一般ユーザーによる貸出申請作成・管理者による承認（API経由でのテストデータ準備）
    - 申請管理画面（`RequestManagementPage.tsx`）の「貸出処理」セクションから承認済み申請IDを入力して貸出→「貸出結果」セクションに申請ID・備品名・貸出日時が表示されることを確認
    - 同一申請IDで再度貸出処理を実行→「この申請は貸出処理できません」のエラーメッセージが表示されることを確認
    - 「返却処理」セクションから同一申請IDと返却時メモを入力して返却→「返却結果」セクションに申請ID・備品名・返却日時が表示されることを確認
    - 同一申請IDで再度返却処理を実行→「この申請は返却処理できません」のエラーメッセージが表示されることを確認
    - ブラウザコンソールエラー監視を行い、意図的なエラー系操作（400を期待する2回の再実行）に対応するネットワークエラーログ以外に、本バックログの新規コードに起因するJavaScript例外等は発生していないことを確認した
- 品質確認コマンド（`python -m ruff check app/`・`python -m mypy app/`、`npm run build`・`npm run lint`）を実行し、いずれもエラーなく完了した。
    - `ruff check app/`で検出された指摘（84件）は、`scheduler.py`の`RET501`/`PLR1711`（既存バックログ由来）、FastAPI `Depends`をデフォルト引数で呼び出すB008指摘（既存エンドポイントにも同様に存在する本プロジェクト標準パターン）であり、いずれも本バックログの変更対象外または既存の許容済みパターンであることを確認した。
    - `mypy app/`で検出された指摘（1件、`database.py:39`のジェネレータ型関連）は、本バックログの変更対象外の既存コードに起因するものであることを確認した。
