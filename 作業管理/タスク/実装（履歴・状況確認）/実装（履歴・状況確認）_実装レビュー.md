# 実装レビュー

## スコープ

実装（履歴・状況確認）バックログの全成果物（`backend/app/schemas.py`・`backend/app/crud.py`・`backend/app/services.py`・`backend/app/main.py`の履歴・状況確認追加部分、`frontend/src/`配下の履歴・状況確認関連修正・新規ファイル）を対象に、`運用ルール/開発ルール/レビュー工程ルール.md`に従い実装レビュー工程を実施する。`実装_チェックリスト.md`・`FastAPI/Pydantic/SQLAlchemy/React_実装_チェックリスト.md`の各項目で確認した。

## レビュー結果

- 各チェックリストの全項目を確認した結果、指摘事項は見つからなかった。
- レビュー工程ルール「指摘が無ければレビュー指摘表の作成は不要」に基づき、レビュー指摘表は作成していない。
- `schemas.py`の`MyLoanRequestListItemResponse`・`OverdueLoanRequestListItemResponse`・`LoanRequestHistoryListItemResponse`の項目名・型・必須/任意・最大桁が、設計書（`設計書/スキーマ（schemas）/履歴・状況確認操作_v1.0.0.md`）と項目単位・順序ともに1対1で一致していることを確認した。
- `main.py`の4エンドポイント（`get_my_loan_requests_endpoint`・`get_overdue_loan_requests_endpoint`・`get_loan_request_history_endpoint`・`export_loan_request_history_endpoint`）が、既存エンドポイントと同じ依存性注入パターン（自分申請一覧取得は`auth.require_password_changed`のみ、他3件は`auth.require_admin`→`auth.require_password_changed`→`get_db`）で実装されており、エンドポイント層からservices層を経由せずcrud.pyを直接呼び出していないこと（レイヤー構成の一方向呼び出し）を確認した。
- docコメントが、処理記述書の「処理概要・パラメータ・戻り値・例外処理・処理フロー」のみを記載する既定の形式に従っており、各処理記述書格納パス（`設計書：サーバー処理（main）/履歴・状況確認/<ファイル名>`）への参照も正しいことを確認した。
- 機能テスト（disposable SQLite + FastAPI `TestClient`、約49件のアサーション）で、以下を確認した。
    - 自分申請一覧取得（F07）：自分の申請のみが返却されること、他ユーザーの申請が含まれないこと（認可境界）。
    - 期限超過一覧取得（F13）：管理者限定であること（一般ユーザーからの403）、承認済み×返却予定日超過・貸出中×返却予定日超過の双方が対象に含まれること。
    - 貸出履歴検索・取得（F17）：管理者限定であること、開始日範囲・資産番号・申請者IDの各検索条件が単独・組み合わせの両方で正しく絞り込まれること、検索条件なしの場合に全件が返却されること。
    - 貸出履歴CSV出力（F17）：UTF-8 BOM付き・ヘッダー行が日本語論理名であること、CSVインジェクション対策（`=`・`+`・`-`・`@`で始まる値の先頭にシングルクォートを付与するエスケープ）が働いていること、検索条件がCSV出力にも反映されること。
    - 「貸出中かつ返却予定日超過」という通常のAPI操作列では再現不能な状態について、`実装（貸出・返却）`バックログと同様の手法（テストデータ準備としてDBの`due_date`列を直接操作）で再現し、期限超過一覧・貸出履歴の双方で正しく扱われることを確認した。
- フロントエンド（`MyRequestsPage.tsx`へのF07追加、`HomePage.tsx`へのF13追加、新規`OverdueLoanRequestsPage.tsx`・`LoanRequestHistoryPage.tsx`）について、Reactチェックリストの非同期状態管理（未着手/読み込み中/復元成功/復元失敗の状態enumeration）・Hooks使用（`react-hooks/set-state-in-effect`アンチパターン）の観点で個別にコードを確認した。
    - いずれの画面も、`useCallback`でデータ取得処理を定義し`useEffect`でマウント時に呼び出す、または単純なfetch-in-effectパターンであり、props駆動の子ローカル状態リセットという`set-state-in-effect`アンチパターンには該当しないことを確認した。
    - `MyRequestsPage.tsx`は、既存の申請取消処理（F06）成功後に一覧を再取得する処理（`await loadMyLoanRequests()`）が正しく追加されていることを確認した。
    - `HomePage.tsx`は、管理者以外では期限超過件数の取得処理自体を実行しない（`useEffect`内で`user.role !== "admin"`の場合に早期return）ことを確認した。
    - `LoanRequestHistoryPage.tsx`のCSV出力処理は、既存の`apiUploadRequest`と同様のエラーハンドリング（401検知含む）を行う新規`apiDownloadRequest`（Blob取得用）を経由しており、`URL.createObjectURL`で生成したURLを`URL.revokeObjectURL`で解放する実装になっていることを確認した。
- Playwright（`frontend/node_modules`に既存インストール済みのPlaywrightパッケージを直接`require`する方式。本バックログ用に新規作成したdisposableスクリプトで実施し、確認後に削除した）を用いて実際にブラウザ（Chromium）を起動し、開発サーバー（バックエンド：disposable SQLiteで`uvicorn`起動、フロントエンド：`npm run dev`のVite開発サーバー）に対して以下の一連の操作を実施し、画面が設計どおりに動作しコンソールエラーが発生しないこと（`CONSOLE_ERRORS_COUNT: 0`）を確認した。
    - 管理者ログイン→初回パスワード変更→ホーム画面（F13の期限超過件数セクションが表示されること）
    - 自分の申請一覧画面（F07の申請状況一覧が表示されること）
    - 期限超過一覧画面（S08、新規画面が表示されること）
    - 貸出履歴画面（S11、新規画面で検索を実行し結果が表示されること、「CSV出力」ボタンのクリックでファイルダウンロードが発生し、ダウンロードされたファイルがUTF-8 BOM付き・CRLF改行であること（`file`コマンドで確認））
    - 検証中、ローカル環境で別プロジェクト（`rag-agent`、無関係のChainlitアプリ）がポート8000の`127.0.0.1`を既に使用していたため、disposable検証用バックエンドが`0.0.0.0:8000`にバインドしても実際のHTTPリクエストが既存の別プロセスに奪われる現象が発生したが、disposable検証用バックエンドをポート8001に変更し、`frontend/vite.config.ts`のプロキシ先を検証中のみ一時的に8001へ変更して対応した。検証完了後に`vite.config.ts`を8000へ正しく戻したことを`git diff`で差分がないことを確認済み（コミット対象には影響なし）。
- 品質確認コマンド（`python -m ruff check app/`・`python -m mypy app/`、`npm run build`・`npm run lint`）を実行し、いずれもエラーなく完了した。
    - `ruff check app/`は本バックログ変更後に99件（変更前84件）であったが、増加分はすべてFastAPI `Depends`/`Query`をデフォルト引数で呼び出すB008指摘であり、既存エンドポイントにも同様に存在する本プロジェクト標準パターンを新規4エンドポイントにも適用した結果であることを確認した。新規の指摘カテゴリ（ルールID）は追加されていない。
    - `mypy app/`で検出された指摘（3件：`database.py`のジェネレータ型関連1件、`scheduler.py`の型スタブ欠如2件）は、変更前から存在する既存コード・既存バックログ由来のものであり、本バックログの変更対象外であることを確認した。
    - `npm run lint`・`npm run build`は、ESLintの指摘0件・TypeScriptの型エラー0件・ビルド成功を確認した。
